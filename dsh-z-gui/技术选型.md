# dsh 桌面 GUI 版 —— 技术选型

> 版本：v0.1（讨论稿）
> 状态：待讨论确认
> 目标：在官方 [deepseek-harness](../deepseek-harness) 基础上改造，产出 **Windows / Linux 桌面 GUI 应用**，内置 Node 运行时、目标机零安装、不依赖外部运行环境。

---

## 1. 目标与边界

| 项目 | 内容 |
|---|---|
| 产品形态 | 桌面 GUI 应用（原生窗口，非浏览器、非纯终端） |
| 核心能力 | 复用 deepseek-harness 完整的 Agent 引擎与对话能力 |
| 运行要求 | Windows / Linux 双平台，**内置 Node 运行时**，目标机无需安装 Node 或任何运行时 |
| 技术偏好 | 当前主流、稳定、社区活跃；务实、低成本改造优先 |

---

## 2. 改造对象的硬约束（调研结论）

在选型前，必须先明确 deepseek-harness 的架构约束，它们直接决定 GUI 技术栈的选择：

1. **引擎是 Node.js / TypeScript**，大型 monorepo（`packages/*` 数十个 workspace 包），纯 ESM。
2. **深度依赖 Node 内部模块**：vendored Cordis 加载器通过 `node-addon-require-builtin` 原生插件访问
   `internal/modules/esm/loader` 实现模块热更新（HMR）（见
   [vendor/loader/src/internal.ts](../deepseek-harness/vendor/loader/src/internal.ts)）。
   ⇒ **必须保留真实 Node 运行时**。Bun 等替代运行时无法提供该内部模块，会导致 HMR 失效（已排除 Bun）。
3. **已有完整 React 前端**（`apps/web` + `packages/client/*`，浏览器 UI），可整体复用于桌面窗口。
4. **profile 插件机制**：运行时从 `$DSH_HOME/profiles/<name>/node_modules` 动态加载插件（如用户已安装的
   webhook 插件）。打包后必须保留该能力。
5. **现有交互入口**：`dsh` CLI 按 profile 启动，shipped profile 为 `web`（启动本地 Web 服务 + React 前端）与
   `headless`（一次性问答）。**桌面 GUI 版的核心工作 = 给 `web` profile 套一个原生窗口壳**。

## 3. 候选技术方案

### 方案 A：Electron（主进程即 Node）

- **思路**：Electron 主进程本身就是一个 Node.js 进程，天然满足"内置 Node 运行时"。把 dsh 的 `web` profile
  （本地 Web 服务 + React 前端）跑在 Electron 主进程内，用 `BrowserWindow` 加载本地前端页面。
- **打包**：electron-builder 产出 Windows 安装包/便携版（.exe）与 Linux（.AppImage / .deb）。
- **优点**
  - 改动最小：复用现有 React 前端与 `web` profile，**几乎不改 deepseek-harness 核心代码**；
  - 天然内嵌 Node，与"自包含发布包"决策 100% 契合；
  - 主流稳定：VS Code、Slack、Notion、Discord 等大量生产级应用基于 Electron；
  - 生态成熟：electron-builder / Electron Forge 跨平台打包、自动更新、托盘、系统集成开箱即用。
- **缺点**
  - 包体较大（约 100–150 MB）；内存占用较高（Chromium + Node）；
  - 不满足"极致轻量"诉求（若用户在意体积与内存，见方案 B）。

### 方案 B：Tauri v2 + Node sidecar（Rust 壳）

- **思路**：Tauri v2（Rust 后端 + 系统 WebView：Windows WebView2 / Linux WebKitGTK）做原生窗口壳；
  Node.js 作为 **sidecar 外部二进制**（按平台内置 Node 运行时）运行 dsh `web` profile 后端；
  WebView 加载本地前端页面，Rust 主进程负责 sidecar 生命周期管理与 IPC 桥接。
- **打包**：Tauri CLI 产出 Windows .exe（MSI/NSIS）与 Linux .deb/.AppImage，sidecar 作为外部资源随包分发。
- **优点**
  - 包体小（约 20–40 MB，含 Node sidecar）；内存占用低；
  - 符合用户对 Rust 技术栈的偏好；Tauri v2 为当前主流稳定框架（2024 年 10 月 2.0 稳定，持续迭代）；
  - 托盘、快捷键、系统集成等能力成熟。
- **缺点**
  - **复杂度显著高于方案 A**：Rust 壳 + sidecar 进程管理 + WebView 与后端通信桥三部分叠加，
    调试与维护链路长（Rust + TS 双栈）；
  - Windows 依赖 WebView2（Win10+ 系统自带，Win7/8 需额外分发）；Linux 依赖 WebKitGTK 系统库；
  - Node sidecar 的进程生命周期、端口分配、崩溃重启、日志重定向等需自研。

### 方案 C：Wails v2（Go + WebView）

- **思路**：Go 后端 + 系统 WebView；Node 引擎同样作为 sidecar 运行 dsh 后端。
- **评价**：与方案 B 面临相同的 sidecar 复杂度，但 Go 生态的桌面壳成熟度与维护度低于 Tauri；
  且主引擎是 Node，Go 优势难以发挥。**不作为首选**，仅作备案。

### 方案 D：本地启动器 + 默认浏览器（无独立窗口）

- **思路**：用轻量启动器（Rust/Go）启动内置 Node 跑 dsh `web` profile，再拉起默认浏览器访问。
- **评价**：改动最小、包体最小，但**没有原生窗口**，不具备托盘、独立进程、离线窗口等桌面体验，
  与"桌面 GUI 应用"目标不符。**排除**。

## 5. 详细方案 A：Electron

### 5.1 总体架构

Electron 主进程本身就是一个 Node.js 进程，**直接内置 Node 运行时**。方案思路：

1. Electron 主进程内加载 dsh CLI 的构建产物，调用其 profile-boot 逻辑启动 `web` profile
   （即"dsh --profile web"，本地起 HTTP/WS 服务并 serve React 前端）；
2. 动态分配本地端口，创建 `BrowserWindow` 加载该前端页面；
3. 持久化与插件机制沿用 `$DSH_HOME/profiles/web/`，**完全不改动 deepseek-harness 核心**。

```
┌──────────────────────────────────────────────────────┐
│              dsh-gui（Electron 应用）                  │
│                                                      │
│  BrowserWindow（Chromium 渲染进程）                    │
│    └── deepseek-harness React 前端（web profile 自带） │
│                ▲ HTTP/WS（localhost:动态端口）         │
│  Main Process（Node.js 运行时，Electron 内置）         │
│    ├── dsh CLI lib（复用：apps/cli 构建产物）          │
│    ├── runProfile('web') → 启动 web 后端 + 前端静态   │
│    ├── 窗口/托盘/生命周期管理（壳代码，新增）           │
│    └── 原生模块 rebuild（electron-rebuild）            │
│                                                      │
│  持久化: $DSH_HOME/profiles/web/（复用，不改）         │
└──────────────────────────────────────────────────────┘
```

### 5.2 关键实现要点

| 要点 | 设计 | 说明 |
|---|---|---|
| 后端承载 | 主进程内 `import` dsh CLI lib，调用 `runProfile('web')` | 复用 [profile-boot.ts](../deepseek-harness/apps/cli/src/profile-boot.ts) 的既有入口，零改动 |
| 端口策略 | 启动前扫描空闲端口，注入 `--port` 或环境变量 | 规避多实例/系统占用冲突 |
| 窗口加载 | `BrowserWindow` 加载 `http://127.0.0.1:<port>` | 直接复用 web profile 前端，无需新增 renderer |
| 原生模块 | 依赖 dsh 的原生 addon（`node-addon-require-builtin`、`better-sqlite3` 等）需针对 **Electron ABI** 重编译 | 通过 `@electron/rebuild` 或 prebuild 处理，这是本方案唯一不可回避的工程点 |
| 进程隔离 | （P1）将 dsh 后端拆为独立 Node 子进程，主进程负责拉起/健康检查/崩溃重启 | 首版可先放主进程内，降低复杂度 |
| 安全 | `contextIsolation: true`、`nodeIntegration: false`、配 CSP | Electron 安全基线 |

### 5.3 技术栈明细

| 层 | 技术 | 说明 |
|---|---|---|
| 桌面壳 | Electron（最新稳定版） | 主进程承载 dsh web 后端 |
| 前端 | 复用 deepseek-harness React 前端 | 零开发 |
| Agent 引擎 | deepseek-harness（Node/TS） | 复用，不改核心 |
| 打包 | electron-builder | Windows：NSIS/portable；Linux：AppImage/deb |
| 原生模块 | @electron/rebuild | 按 Electron ABI 重编译 dsh 的 addon 依赖 |
| 系统集成 | 托盘 / 开机自启 / 协议唤起（P1） | electron-builder + 少量壳代码 |

### 5.4 建议目录结构

```
dsh-z-gui/
├── 技术选型.md
├── app/                     # Electron 壳（新增，独立于 deepseek-harness）
│   ├── package.json
│   ├── main/
│   │   ├── index.js         # 入口：boot dsh web + 创建窗口
│   │   ├── dsh-boot.js      # 封装 runProfile('web') 与端口分配
│   │   ├── tray.js          # （P1）托盘
│   │   └── lifecycle.js     # （P1）子进程化/崩溃重启
│   ├── preload/index.js     # 安全 IPC 桥
│   └── resources/           # 图标等
├── scripts/                 # 构建/打包脚本（win/linux）
└── docs/
```

deepseek-harness 保持独立，通过构建脚本把其 `apps/cli` 产物 + 依赖装入 Electron app 的 `node_modules`。

### 5.5 实现路径（P0）

1. 在 deepseek-harness 仓库内完成 `pnpm install` + `pnpm build`（产出 `apps/cli/lib`）；
2. 生成 dsh CLI 的"依赖闭包"（node_modules 全量），作为 Electron app 的依赖安装；
3. `@electron/rebuild` 重编译原生模块；
4. 壳代码：boot web profile → 动态端口 → BrowserWindow 加载 → 退出清理；
5. electron-builder 出 Windows/Linux 包，目标机实测。

### 5.6 工作量与风险

- 工作量：壳代码约 200–400 行 JS + 打包配置；**主要成本在原生模块 rebuild 与打包调试**。
- 主要风险：原生模块 ABI 重编译（标准解法，风险可控）；包体 ~100–150MB（无预算约束，可接受）。

## 6. 详细方案 B：Tauri v2 + Node sidecar

### 6.1 总体架构

Tauri v2（Rust 壳 + 系统 WebView）做原生窗口；**Node.js 作为 sidecar 外部二进制**（按平台内置官方
Node 预编译二进制）运行 dsh `web` profile 后端；WebView 加载本地前端页面；Rust 主进程负责
sidecar 全生命周期治理。

```
┌──────────────────────────────────────────────────────┐
│             dsh-gui（Tauri v2 应用）                   │
│                                                      │
│  WebView（系统渲染：Windows WebView2 / Linux WebKitGTK）│
│    └── deepseek-harness React 前端                    │
│                ▲ HTTP/WS（localhost:动态端口）         │
│  Rust 主进程（Tauri 壳）                              │
│    ├── sidecar 进程管理：拉起/健康检查/崩溃重启/日志    │
│    ├── 端口分配与 WebView 配置                         │
│    └── 托盘/系统集成                                  │
│                ▲ 内置 Node sidecar（node 二进制）      │
│  dsh web 后端（独立进程：node runProfile('web')）       │
│                                                      │
│  持久化: $DSH_HOME/profiles/web/（复用，不改）         │
└──────────────────────────────────────────────────────┘
```

### 6.2 关键实现要点

| 要点 | 设计 | 说明 |
|---|---|---|
| sidecar 打包 | Tauri `externalBin` 内置 Node 二进制，按平台命名分发（`node-x86_64-pc-windows-msvc.exe` / `node-x86_64-unknown-linux-gnu`） | 官方预编译二进制，随包分发即"内置 Node" |
| 启动 | Rust 以 `Command`/`Command::new_sidecar` 拉起 `node runProfile('web')` | 传动态端口与 `$DSH_HOME` 环境 |
| 端口策略 | 绑定端口 0 或扫描空闲端口，实际端口回传 WebView | 规避冲突 |
| 通信 | WebView 直接加载 `http://127.0.0.1:<port>`，复用 dsh 既有 HTTP/WS API | 无需额外 IPC 协议 |
| 生命周期 | Rust 监听 sidecar 退出 → 自动重启；应用退出 → 先杀 sidecar 再退 | 需自研进程治理 |
| 系统依赖 | Windows WebView2（Win10+ 内置）、Linux WebKitGTK | 目标机零安装的前提是系统自带 WebView |
| 原生模块 | sidecar 用官方 Node，ABI 与系统 Node 一致，无 rebuild 问题 | 比方案 A 简单 |

### 6.3 技术栈明细

| 层 | 技术 | 说明 |
|---|---|---|
| 桌面壳 | Tauri v2（Rust） | 原生窗口 + 系统 WebView |
| sidecar | 官方 Node.js 二进制 + dsh web 后端 | 随包分发，内置运行时 |
| 前端 | 复用 deepseek-harness React 前端 | 零开发 |
| Agent 引擎 | deepseek-harness（Node/TS） | 复用，不改核心 |
| 打包 | Tauri CLI | Windows：NSIS/MSI；Linux：.deb/AppImage |
| 系统集成 | Tauri 插件（托盘/单实例/自动更新） | 生态较成熟 |

### 6.4 建议目录结构

```
dsh-z-gui/
├── 技术选型.md
├── src-tauri/               # Rust 壳
│   ├── src/main.rs          # 入口：sidecar 治理 + 窗口
│   ├── src/sidecar.rs       # 进程管理/重启/日志
│   ├── tauri.conf.json      # externalBin: node sidecar
│   └── capabilities/
├── app/                     # dsh web 后端载体（构建产物 + node_modules）
├── resources/               # 内置 node 二进制（win/linux）
├── scripts/
└── docs/
```

### 6.5 实现路径（P0）

1. 在 deepseek-harness 仓库内完成 `pnpm install` + `pnpm build`；
2. 生成 dsh CLI 依赖闭包（node_modules 全量）+ 官方 Node 二进制，作为 sidecar 资源；
3. Rust 壳：sidecar 启动/健康检查/崩溃重启/端口分配/日志；
4. Tauri 窗口加载 localhost 前端，实测 Windows 与 Linux；
5. Tauri CLI 出 Windows/Linux 包。

### 6.6 工作量与风险

- 工作量：Rust 壳约 500–1000 行 + sidecar 治理自研 + Tauri 配置，**约为方案 A 的 2–3 倍**；
  双栈（Rust + Node/TS）调试链路更长。
- 主要风险：sidecar 进程治理的边界情况（端口抢占、崩溃循环、日志轮转、环境变量传递）需自研测试；
  Linux 目标机需 WebKitGTK 系统库；Windows Win7/8 无 WebView2 需要外部分发。

## 7. 推荐结论（待定）

- **默认倾向**：方案 A（Electron）——无包体预算约束、复用零改动、单一语言栈、生态成熟、工程风险最低。
- **转向方案 B 的条件**：坚持 Rust 技术栈、或未来出现"包体 ≤50MB / 内存敏感 / 低配机运行"硬性要求。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Electron 原生模块 ABI 重编译 | 打包失败/运行异常 | `@electron/rebuild`；失败则降级为系统 Node 侧子进程方案 |
| sidecar 进程治理（仅方案 B） | 崩溃/端口/日志问题 | 自研测试 + 看门狗重启 |
| dsh web profile 端口冲突 | 多实例/占用冲突 | 动态分配端口 |
| 前端与本地后端跨域/CSP | 页面加载失败 | localhost 加载 + 配置 CSP |
| 插件安装路径依赖 `$DSH_HOME` | 打包后路径语义变化 | 保留 `$DSH_HOME` 解析逻辑，文档化默认路径 |
| Linux WebKitGTK / Win WebView2 依赖（仅方案 B） | 目标机缺库 | 方案 A 无此问题 |

## 12. 待讨论决策点

1. **技术栈确认**：主选 Electron（方案 A）还是坚持 Rust 的 Tauri + sidecar（方案 B）？
2. **包体/内存预算**：是否对包体（≤150MB）与内存有硬性预算？若有 → 方案 B。
3. **界面策略**：完全复用现有 React 前端，还是做一层定制化的桌面主题壳层？
4. **分发形态**：Windows 需要安装版 + 便携版两种吗？Linux 要 AppImage 还是 deb？
5. **首版范围**：P0 只做"引擎跑通 + 窗口对话"，是否包含托盘、开机自启、自动更新等 P1 能力？
